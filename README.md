# NoWatermark — 本地批量图片去水印工具

纯本地、离线的 Android 去水印工具，面向 Redmi K60E / HyperOS 2.0（Android 15）开发。
**图片全程留在本机处理，不联网、不上传任何图片。**

---

## 功能对照

| 需求 | 实现 |
| --- | --- |
| 选本地文件夹、递归扫描子文件夹 | 内置文件夹选择器，递归遍历，支持数万张图片（只收集路径，不预加载图片） |
| 自动区分有/无水印，无水印直接跳过 | 启发式检测，无水印图片**不进入后续任何处理**；允许少量误判，由你人工复核 |
| 强制预览确认 | 扫描后只列出有水印图片，**每张同步显示拍摄日期**；必须手动勾选才处理，未勾选的绝不处理 |
| 只修复水印区域、保留原图其余内容 | Telea 快速行进修复算法，**仅在检测到的水印矩形内改写像素**，区域外像素逐位不变 |
| 原图分辨率 / 尺寸 / 色彩保留 | 按原始尺寸解码与输出，不缩放、不裁剪；输出质量 100 |
| 不覆盖原图 | 输出到独立文件夹，保留原文件名与相对子目录结构 |
| 进度 / 暂停 / 取消 | 前台服务 + 通知栏，实时显示扫描与处理进度，支持暂停、继续、取消 |
| 处理日志 | 界面内可查看最近日志，完整日志写入应用私有目录 |
| 稳定优先、无花哨 UI | 原生 Android View，零 native 依赖，无第三方图像库 |

## 构建与安装

### GitHub Actions 云端打包（推荐）

仓库已内置 `.github/workflows/build.yml`。把工程推送到 GitHub 的 `main` 或 `master` 分支，
或在 Actions 页面手动触发 `Build NoWatermark APK`：

1. Actions 会自动准备好 JDK 17 + Android SDK 35，并使用工程自带的 Gradle wrapper；
2. 自动生成一个临时签名证书对 Release 包签名；
3. 构建完成后在本次运行的 Artifacts 中下载 `NoWatermark-release`，解压得到 `app-release.apk`。

### 本地构建（可选）

需要 JDK 17 + Android SDK（platform 35、build-tools 35.0.0）。工程已自带 Gradle wrapper：

```bash
./gradlew assembleRelease                 # Windows 用 gradlew.bat assembleRelease
```

产物在 `app/build/outputs/apk/release/`。
（工程内已包含 `gradle-wrapper.jar`，无需再运行 `gradle wrapper`。）

### 安装到 Redmi K60E / HyperOS

1. 把 APK 传到手机安装（HyperOS 可能对未知来源安装有提示，按系统引导允许）。
2. 首次打开，**按提示授予「允许管理所有文件」权限**：
   应用内点「前往开启」→ 系统设置中打开本应用的「允许管理所有文件」。
   这是 Android 11+ 递归读取任意文件夹和写入结果目录的必要权限。
3. 允许通知（用于后台任务的进度显示）。

## 使用流程

1. **图片来源文件夹**：点「选择文件夹」，选中要扫描的目录（会递归读取其子目录）。
2. **结果输出文件夹**：点「选择文件夹」，选中另一个独立目录。
   ⚠️ 不能与来源文件夹相同，也不能是来源文件夹的父/子目录。
3. **检测灵敏度**：
   - 偏「保守」：判定更严格，进入确认列表的图片更少，可能漏掉淡水印；
   - 偏「宽松」：判定更宽松，会有更多误判，但不易漏掉水印。
   默认 50%。可先用少量图片试扫，再决定是否调整。
4. 点「开始扫描」。扫描期间显示进度，可暂停 / 取消。
5. 扫描结束进入**确认列表**：只显示判定有水印的图片，每张带缩略图、文件名、**拍摄日期**和检测区域数。
   - 点图片可放大预览，红框标出将修复的区域；
   - 用「全选 / 取消全选 / 反选」或直接勾选每一张；
   - **只有勾选的图片会被处理。**
6. 点「开始处理勾选的 N 张」，返回主界面看处理进度。完成后结果按原文件名写入输出目录，
   **原图保持不变**，你可自行核对后删除原图。

## 水印检测与修复的实现说明（请务必阅读）

### 检测是启发式的，不是 AI 模型

本工具**不依赖任何在线接口或大模型**，用纯图像信号分析判断水印：

- 先用大半径模糊估计图片的低频背景，求“叠加层残差”；
- 统计全图残差的主方向——半透明水印会把大片像素朝同一颜色方向推，而自然纹理正负相消；
- 对残差投影做阈值化、形态学闭运算、连通域分析；
- 结合区域面积、长宽比、位置（越靠边越像水印）等特征打分。

因此：

- **会有误判和漏判**。误判的图片会进入确认列表，由你人工核对（这正是强制确认流程的意义）；
- 对**半透明文字 / Logo 水印、位于画面边缘或角落的水印**效果最好；
- 对极淡的水印、与画面纹理高度融合的水印、平铺满屏水印，可能漏检；
- 完全无规律、只出现在一张图上的标记，无法与照片内容区分。

调高灵敏度可减少漏检（代价是误判变多）。

### “只改水印区域、其余像素不变”的边界

修复使用 Telea 快速行进算法，在检测区域的矩形 mask 内，由边界向中心按纹理走势填充。
**在解码后的像素数组层面，mask 之外的 RGB 值一个字节都不会改动**（已用合成图测试验证：区域外改动像素数 = 0）。

但磁盘文件层面存在一个客观限制，需要说明：

- **PNG 原图 → PNG 输出**：无损保存，水印区域外像素逐位不变，完全满足要求。
- **JPEG 原图 → JPEG 输出**：JPEG 是有损格式，保存时必须对整张图重新编码。
  虽然本工具用最高质量（100）重编码，但**未修改区域的像素值可能发生极微小的变化**（肉眼不可见，
  分辨率、尺寸、色彩、画面内容均不变）。这是 JPEG 格式本身决定的，任何可编辑的 JPEG 处理都无法避免；
  若你需要严格的逐位不变，请先把原图转为 PNG 再处理。

### 大批量稳定性设计

- 扫描阶段只收集文件路径，不加载图片；检测阶段把图片采样到最多 1000 像素长边再分析；
- 处理阶段一次只解码一张，修复后立即回收；确认列表缩略图用 LruCache + 固定线程池异步加载；
- 任务放在前台服务单线程执行，配合通知保持进程存活；
- 暂停 / 取消是协作式的，在每个图片处理的安全点检查，不会中途留下半张损坏的输出文件
  （输出是完整写完后才生成的）。

## 工程结构

```
NoWatermark/
├── app/src/main/java/com/sopro/nowatermark/
│   ├── MainActivity.java              主界面：授权/选目录/参数/进度/日志
│   ├── core/
│   │   ├── algo/                      纯 Java 算法（可独立编译测试）
│   │   │   ├── WatermarkAnalyzer.java   水印检测：残差投影 + 连通域打分
│   │   │   ├── TeleaInpainter.java      Telea 快速行进修复
│   │   │   ├── BoxBlur.java             可分离箱式模糊
│   │   │   ├── ConnectedComponents.java 连通域 / 形态学
│   │   │   └── Region.java              归一化水印区域
│   │   ├── WatermarkDetector.java      Bitmap 解码 + 检测封装
│   │   ├── ImageProcessor.java         单图修复与保存
│   │   ├── MaskBuilder.java            归一化区域 -> 原图 mask
│   │   ├── FileScanner.java            递归文件扫描
│   │   ├── ExifHelper.java             拍摄日期读取
│   │   └── ImageInfo.java              数据模型
│   ├── task/
│   │   ├── TaskService.java            前台服务，执行扫描/处理
│   │   └── TaskManager.java            任务状态机，暂停/取消/进度/日志
│   ├── ui/                             确认列表、预览、文件夹选择器
│   └── util/                           设置与日志
├── app/src/main/res/                   布局与资源
├── .github/workflows/build.yml         GitHub Actions 打包
└── README.md
```

核心算法（`core/algo/`）不依赖任何 Android API，可用普通 JDK 编译并单独测试。

- 所有图片只在应用进程内解码、分析、修复，输出到用户指定目录；
